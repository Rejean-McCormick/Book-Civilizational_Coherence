# **Chapitre 19 — Multi-Scale Institutions**

## **Fonction du chapitre dans le livre**

Les chapitres 17 et 18 ont établi qu’une même architecture peut être :

\[  
CanonicalKernel  
\\rightarrow  
SovereignInstances  
\\rightarrow  
Divergence  
\\rightarrow  
SelectiveInteroperability  
\]

Mais jusqu’ici, le mot **instance** est resté relativement abstrait.

Or une instance peut correspondre à :

* une personne;  
* une équipe;  
* une association;  
* une entreprise;  
* un hôpital;  
* une municipalité;  
* un ministère;  
* un réseau scientifique;  
* une organisation internationale.

Ces systèmes ne diffèrent pas seulement par leur nombre d’utilisateurs. Ils diffèrent aussi par :

* leur mandat;  
* leurs responsabilités;  
* leur rayon d’action;  
* leur structure de gouvernance;  
* leurs obligations de confidentialité;  
* les conséquences de leurs décisions.

La question centrale du chapitre devient :

> **Comment une même architecture sociotechnique peut-elle être utile à des institutions de plusieurs échelles sans supposer qu’elles doivent fonctionner de la même manière, appartenir à une même hiérarchie ou être absorbées dans une instance globale?**

L’idée centrale est :

> **La cohérence multi-échelle ne consiste pas à reproduire la même institution à toutes les tailles. Elle consiste à permettre à des instances de tailles, mandats et gouvernances différents de fonctionner souverainement tout en composant sélectivement leurs capacités lorsque leur relation l’exige.**

Le chapitre doit également empêcher plusieurs confusions :

\[  
Scale\\neq Openness  
\]

\[  
Scale\\neq Connectivity  
\]

\[  
Scale\\neq Governance  
\]

Une grande instance n’est pas nécessairement :

* publique;  
* démocratique;  
* fédérée.

Et une petite instance n’est pas nécessairement :

* privée;  
* isolée;  
* informelle.

---

# **1\. Opening — A Person Is Not a Small State**

Commencer par une erreur architecturale fréquente.

Supposons qu’une architecture fonctionne très bien pour :

> une équipe de vingt personnes.

Peut-on simplement multiplier :

* le nombre d’utilisateurs;  
* les niveaux hiérarchiques;

et obtenir :

> une institution mondiale?

Non nécessairement.

Inversement, une architecture conçue pour :

> un gouvernement national

peut être absurde pour :

> une personne organisant sa thèse.

### **Formulation d’ouverture**

> **Scale changes the nature of coordination problems, not merely their quantity.**

En français :

> **Changer d’échelle transforme la nature des problèmes de coordination, pas seulement leur quantité.**

---

# **2\. Multi-Scale Does Not Mean Fractal**

Éviter le terme **fractal** comme description principale.

Une personne, un hôpital et une organisation mondiale ne sont pas :

> la même structure répétée géométriquement.

Ils peuvent toutefois utiliser :

> une grammaire architecturale commune.

Donc :

\[  
SharedArchitecture  
\\neq  
IdenticalInstitutionalStructure  
\]

Le terme correct ici est simplement :

> **multi-scale architecture — architecture multi-échelle.**

---

# **3\. The Fundamental Unit Is the Instance**

Clarification à figer :

> **L’unité fondamentale de cette architecture est l’instance souveraine.**

Pas :

* UCKK;  
* organisation mondiale;  
* utilisateur individuel;  
* serveur central.

Une instance est :

> un déploiement opérationnel disposant de son propre contexte, de ses données, de sa configuration et de ses règles applicables.

---

# **4\. Working Definition of an Instance**

Une formulation possible :

> **An instance is an operationally bounded realization of the architecture with its own configuration, data, permissions, governance profile and relationship to other instances.**

Version française :

> **Une instance est une réalisation opérationnellement délimitée de l’architecture, disposant de sa propre configuration, de ses données, de ses permissions, de son profil de gouvernance et de ses relations avec d’autres instances.**

---

# **5\. A Compact Instance Model**

On peut utiliser :

# **\[**

# **Instance**

Kernel  
\+  
Configuration  
\+  
Modules  
\+  
GovernanceProfile  
\+  
Data  
\+  
LocalExtensions  
\]

### **Traduction littérale**

Une instance combine le noyau architectural avec une configuration, des modules, un profil de gouvernance, des données et éventuellement des extensions locales.

### **Sens**

Le même noyau n’implique pas :

> la même institution.

### **Statut**

**Modèle architectural conceptuel.**

# **6\. Scale Is One Axis Among Several**

Introduire quatre axes indépendants.

### **Scale**

\[  
Individual  
\\rightarrow  
Team  
\\rightarrow  
Organization  
\\rightarrow  
Local  
\\rightarrow  
Regional  
\\rightarrow  
National  
\\rightarrow  
Global  
\]

### **Openness**

\[  
Private  
\\leftrightarrow  
Public  
\]

### **Connectivity**

\[  
Hermetic  
\\leftrightarrow  
Federated  
\]

### **Governance**

Par exemple :

* individual;  
* hierarchical;  
* professional;  
* cooperative;  
* democratic;  
* hybrid.

### **Principe**

Ces axes ne doivent pas être confondus.

---

# **7\. Scale Is Not Openness**

Une organisation mondiale peut être :

> totalement privée.

Une personne peut publier :

> une instance entièrement publique.

Donc :

\[  
Scale  
\\neq  
Openness  
\]

---

# **8\. Scale Is Not Connectivity**

Une grande organisation peut utiliser :

> une instance hermétique.

Une petite équipe peut être :

> intensément fédérée avec plusieurs réseaux.

Donc :

\[  
Scale  
\\neq  
Connectivity  
\]

---

# **9\. Scale Is Not Governance**

Une grande entreprise peut être :

> hiérarchique.

Une petite coopérative :

> démocratique.

Une organisation internationale :

> hybride.

Donc :

\[  
Scale  
\\neq  
Governance  
\]

---

# **10\. Connectivity Is Not Openness**

Une instance peut être :

> privée mais connectée.

Exemple :

deux hôpitaux échangent :

> des données autorisées

sans que celles-ci deviennent :

> publiques.

Donc :

\[  
Federated  
\\neq  
Public  
\]

Cette distinction prépare directement le chapitre 20\.

---

# **11\. A Personal Instance**

Commencer par le niveau le plus petit.

Une personne peut utiliser une instance pour :

* recherche;  
* thèse;  
* projets;  
* apprentissage;  
* connaissances personnelles.

Elle peut fonctionner :

* seule;  
* offline;  
* sans gouvernance collective complexe.

### **Point**

Le système reste utile même lorsqu’il n’existe :

> aucun problème démocratique.

---

# **12\. Individual Governance**

Dans une instance personnelle :

\[  
DecisionAuthority=User  
\]

La gouvernance peut être presque triviale.

Cela montre pourquoi :

> Konnaxion ne doit pas imposer une démocratie universelle à toutes les instances.

---

# **13\. Personal Does Not Mean Isolated**

Une personne peut ensuite :

* importer un Kristal;  
* publier un artefact;  
* contribuer à une instance scientifique.

Donc :

\[  
PersonalInstance  
\\rightarrow  
SelectiveContribution  
\\rightarrow  
LargerInstance  
\]

sans abandonner :

> l’instance personnelle.

---

# **14\. A Team Instance**

Une équipe peut avoir :

* projets;  
* tâches;  
* décisions;  
* documentation;  
* rôles.

La gouvernance devient plus complexe :

* qui décide?  
* qui exécute?  
* qui modifie?

Mais il n’est pas encore nécessaire :

> d’importer toute la structure d’une institution nationale.

---

# **15\. An Organizational Instance**

À l’échelle d’une entreprise ou association apparaissent :

* départements;  
* rôles;  
* politiques;  
* données internes;  
* responsabilités juridiques.

Le problème devient :

> coordination entre sous-unités.

---

# **16\. A Hospital Instance**

Un hôpital possède :

* gouvernance clinique;  
* opérations;  
* données extrêmement sensibles;  
* réglementation;  
* relations avec autorités externes.

Il peut être :

\[  
Large  
\+  
PrivateData  
\+  
Federated  
\+  
Professional/HierarchicalGovernance  
\]

Ce cas montre clairement :

> les axes sont indépendants.

---

# **17\. A Municipal Instance**

Une municipalité ajoute :

* légitimité politique;  
* participation publique;  
* services administratifs;  
* budgets;  
* obligations de transparence.

Elle peut donc combiner :

\[  
DemocraticGovernance  
\+  
HierarchicalExecution  
\]

Comme vu au chapitre 16\.

---

# **18\. A National Instance**

À l’échelle nationale apparaissent :

* nombreux domaines;  
* multiples juridictions internes;  
* institutions autonomes;  
* conflits d’intérêts;  
* diversité linguistique;  
* fort pouvoir potentiel.

### **Point central**

Une instance nationale ne doit pas nécessairement :

> absorber toutes les instances locales.

---

# **19\. A Global Instance**

Une organisation mondiale peut servir à :

* connaissance de référence;  
* coordination internationale;  
* analyse globale.

Mais :

\[  
GlobalInstance  
\\neq  
GlobalSovereignInstance  
\]

Une instance mondiale peut être :

> limitée par un mandat précis.

### **Exemple**

Une instance globale de santé ne devrait pas automatiquement gouverner :

* éducation;  
* économie;  
* politique locale.

---

# **20\. Civilizational Coherence Does Not Require One World Instance**

Relation fondamentale :

\[  
CivilizationalCoherence  
\\neq  
OneGlobalInstance  
\]

Une architecture cohérente peut ressembler à :

\[  
ManyLocalInstances  
\+  
RegionalInstances  
\+  
SpecializedGlobalInstances  
\+  
SelectiveCouplings  
\]

### **Formulation forte**

> **Civilizational scale need not imply civilizational centralization.**

---

# **21\. Global Does Not Mean General-Purpose**

Une instance peut être :

> mondiale

mais extrêmement spécialisée.

Exemple :

> réseau mondial d’agronomes.

Elle peut avoir :

* très grande portée géographique;  
* petit domaine fonctionnel.

Donc il faut distinguer :

\[  
GeographicScale  
\]

de :

\[  
FunctionalScope  
\]

---

# **22\. Scale Is Multidimensional Too**

Une institution peut être grande selon :

* nombre d’utilisateurs;  
* territoire;  
* budget;  
* impact;  
* diversité fonctionnelle.

Donc :

\[  
Scale  
\]

n’est pas forcément :

> une seule variable.

### **Formulation**

> **Institutional scale should be understood as a profile of reach and consequence, not merely user count.**

---

# **23\. Scope Is Often More Important Than Size**

Une petite unité peut contrôler :

> une infrastructure critique nationale.

Une énorme communauté peut prendre :

> aucune décision coercitive.

Donc :

\[  
UserCount  
\\neq  
InstitutionalPower  
\]

C’est important pour :

> proportionnalité des contre-pouvoirs.

---

# **24\. Mandate Defines a Boundary**

Une instance doit idéalement posséder :

> un mandat identifiable.

### **Exemple**

Une agence de santé :

> santé publique.

Pas :

> toute décision humaine imaginable.

### **Principe**

\[  
Mandate  
\\rightarrow  
LegitimateScopeOfAction  
\]

Cela limite :

> l’expansion fonctionnelle silencieuse.

---

# **25\. Scale Creep**

Une institution peut commencer :

> petite et spécialisée.

Puis étendre progressivement :

* son territoire;  
* ses données;  
* son autorité.

On peut appeler cela :

> **scale creep** ou **scope creep** selon le cas.

### **Risque**

\[  
UsefulLocalFunction  
\\rightarrow  
Expansion  
\\rightarrow  
CrossDomainPower  
\]

Cela rejoint :

> capture.

---

# **26\. Larger Scale Increases Coordination Reach**

Une instance plus large peut :

* agréger plus d’information;  
* coordonner plus d’acteurs;  
* mutualiser des ressources.

Donc :

\[  
Scale\\uparrow  
\]

peut augmenter :

\[  
CoordinationCapacity  
\]

dans certains contextes.

---

# **27\. Larger Scale Also Increases Distance**

Mais elle peut augmenter :

* distance aux réalités locales;  
* abstraction;  
* délai;  
* bureaucratie.

Donc :

\[  
Scale\\uparrow  
\]

peut produire :

\[  
ContextLoss\\uparrow  
\]

### **Tension centrale**

> plus haut niveau \= vue plus large, mais souvent moins de détail local.

---

# **28\. Local Knowledge**

Les acteurs locaux possèdent souvent :

* contexte;  
* expérience;  
* détails.

Une autorité supérieure possède davantage :

* comparaison;  
* ressources;  
* coordination interlocale.

Donc :

\[  
LocalKnowledge  
\]

et :

\[  
GlobalView  
\]

sont :

> complémentaires.

Pas substituables.

---

# **29\. The Scale Composition Problem**

Le problème n’est donc pas :

> choisir local ou global.

Il devient :

> **quelles informations et décisions doivent exister à quel niveau, et comment les niveaux se composent-ils?**

---

# **30\. Functional Subsidiarity**

Introduire un principe plus général que la subsidiarité opérationnelle du chapitre 16 :

> **A function should remain at the lowest scale capable of performing it adequately unless a higher scale creates a demonstrable coordination advantage.**

Version française :

> **Une fonction devrait rester au niveau le plus bas capable de l’assurer correctement, sauf lorsqu’une échelle supérieure apporte un avantage de coordination démontrable.**

### **Statut**

**Principe de design**, pas loi politique universelle.

---

# **31\. Why the Lowest Adequate Scale?**

Parce que le local possède souvent :

* information;  
* responsabilité directe;  
* adaptation.

Et réduit :

* dépendance centrale.

Mais :

> « lowest » ne signifie pas automatiquement « best ».

Le niveau local peut manquer :

* ressources;  
* expertise;  
* capacité d’internaliser les externalités.

---

# **32\. Subsidiarity Has Failure Modes**

Une politique totalement locale peut échouer si :

* pollution traverse les frontières;  
* épidémie traverse les régions;  
* standards doivent interagir.

Donc :

\[  
LocalAutonomy  
\\not\\Rightarrow  
AdequateSystemCoordination  
\]

---

# **33\. Externalities Create Scale Requirements**

Si une action locale produit des effets :

> ailleurs,

alors un niveau supérieur ou transversal peut devenir nécessaire.

### **Relation**

\[  
CrossBoundaryExternality  
\\rightarrow  
NeedForCrossBoundaryCoordination  
\]

### **Statut**

**Principe analytique.**

---

# **34\. Shared Resources Can Create Scale Requirements**

Même chose pour :

* infrastructures;  
* budgets;  
* rare expertise.

Une petite institution peut demander :

> aide d’un niveau supérieur

sans perdre :

> toute sa souveraineté locale.

---

# **35\. Escalation Across Scales**

Le chapitre 16 avait :

\[  
BlockedTask  
\\rightarrow  
Escalation  
\]

Ici, on généralise :

\[  
LocalIssue  
\\rightarrow  
HigherScaleCoordination  
\]

lorsque :

* autorité;  
* ressources;  
* impact;

dépassent le niveau local.

---

# **36\. Upward Escalation Does Not Mean Permanent Transfer**

Une instance peut demander :

> assistance temporaire.

Puis reprendre :

> contrôle local.

Donc :

\[  
Escalation  
\\neq  
PermanentCentralization  
\]

---

# **37\. Downward Delegation**

Inversement, une grande instance peut déléguer :

> une fonction.

\[  
HigherScaleMandate  
\\rightarrow  
LocalExecution  
\]

Ce modèle est courant :

* État;  
* municipalité;  
* hôpital.

### **Important**

Le mandat et l’exécution peuvent exister :

> à des niveaux différents.

---

# **38\. Decision Scale and Execution Scale Can Differ**

Relation importante :

\[  
DecisionScale  
\\neq  
ExecutionScale  
\]

Une politique nationale peut être :

> exécutée localement.

Une connaissance locale peut :

> influencer une décision globale.

L’architecture doit supporter :

> ces croisements.

---

# **39\. Knowledge Scale and Authority Scale Can Differ**

Une institution mondiale peut produire :

> connaissance.

Mais la décision reste :

> nationale.

Donc :

\[  
KnowledgeScale  
\\neq  
AuthorityScale  
\]

Cela prolonge le chapitre 15\.

---

# **40\. Attention Scale Can Differ Too**

Un problème local peut devenir :

> mondialement pertinent.

Un problème mondial peut n’exiger l’attention que :

> de quelques spécialistes.

Donc :

\[  
AttentionScale  
\\neq  
GeographicScale  
\]

---

# **41\. One Problem Can Exist at Multiple Scales Simultaneously**

Exemple :

> maladie émergente.

Elle existe :

* chez un patient;  
* dans un hôpital;  
* dans une région;  
* mondialement.

Chaque niveau voit :

> une autre partie du problème.

### **Formulation**

> **Multi-scale coordination is often not a sequence of levels but simultaneous observation and action at several scales.**

---

# **42\. Avoid the Simple Pyramid Model**

Une représentation exclusivement :

\[  
Individual  
\\rightarrow  
Local  
\\rightarrow  
Regional  
\\rightarrow  
National  
\\rightarrow  
Global  
\]

est trop simple.

Pourquoi?

Les institutions peuvent aussi se connecter :

* horizontalement;  
* transversalement.

Exemple :

> deux hôpitaux de pays différents.

Donc l’architecture ressemble davantage à :

> un réseau multi-échelle.

---

# **43\. Horizontal Coordination**

Instances de même échelle :

\[  
Hospital\_A  
\\leftrightarrow  
Hospital\_B  
\]

peuvent coopérer directement.

Sans passer systématiquement par :

\[  
NationalAuthority  
\]

si leur mandat le permet.

### **Bénéfice**

Réduction de :

* latence;  
* central bottleneck.

---

# **44\. Vertical Coordination**

Certaines relations sont réellement verticales :

\[  
Local  
\\leftrightarrow  
Regional  
\\leftrightarrow  
National  
\]

parce que :

* mandat;  
* financement;  
* autorité;

sont structurés ainsi.

L’architecture doit supporter :

> les deux formes.

---

# **45\. Cross-Scale Networks**

Une personne peut participer directement à :

> un réseau scientifique global.

Son institution locale n’est pas forcément :

> intermédiaire obligatoire.

Donc :

\[  
Individual  
\\leftrightarrow  
GlobalDomainNetwork  
\]

peut coexister avec :

\[  
Individual  
\\rightarrow  
LocalOrganization  
\]

---

# **46\. Institutional Membership Is Many-to-Many**

Une personne peut appartenir à :

* université;  
* ordre professionnel;  
* association;  
* réseau mondial.

Donc :

\[  
Person  
\\not\\subset  
OneInstitutionOnly  
\]

Cette pluralité empêche :

> une hiérarchie institutionnelle unique.

---

# **47\. Overlapping Institutions**

Deux institutions peuvent exercer :

> des fonctions différentes sur les mêmes personnes.

### **Exemple**

Médecin :

* hôpital;  
* ordre professionnel;  
* université;  
* association scientifique.

Une bonne architecture doit permettre :

> superposition de mandats.

---

# **48\. Overlap Can Create Conflict**

Deux institutions peuvent émettre :

> des règles contradictoires.

Alors :

\[  
Mandate\_A  
\]

et :

\[  
Mandate\_B  
\]

peuvent entrer en conflit.

Le système doit pouvoir :

* détecter;  
* attribuer;  
* escalader.

Il ne peut pas supposer :

> une hiérarchie universelle déjà connue.

---

# **49\. Jurisdiction Is a Relationship**

Une règle ne vaut pas forcément :

> partout.

Elle possède :

* autorité;  
* domaine;  
* population;  
* territoire;  
* durée.

Donc une décision devrait idéalement pouvoir préciser :

\[  
Decision  
\+  
Jurisdiction  
\]

---

# **50\. Jurisdiction Is Not the Same as Geography**

Une institution professionnelle peut avoir :

> compétence mondiale sur ses membres

sans contrôler :

> un territoire.

Donc :

\[  
Jurisdiction  
\\neq  
Territory  
\]

nécessairement.

---

# **51\. Domain Jurisdiction**

Une institution peut avoir un mandat :

> sur un domaine.

Exemple :

* sécurité;  
* santé;  
* finances.

Donc :

# **\[**

# **Authority**

Authority(domain,scope,context)  
\]

reprenant la logique du chapitre 7\.

---

# **52\. Multi-Scale Institutions Need Explicit Boundaries**

Plus les instances se chevauchent, plus il devient important de savoir :

* qui peut décider quoi;  
* pour qui;  
* dans quel contexte.

### **Formulation**

> **Multi-scale coherence requires explicit boundaries more than uniform hierarchy.**

---

# **53\. Scale Mismatch**

Définir un concept utile :

> **scale mismatch** : situation où le niveau auquel un problème est observé, gouverné ou exécuté ne correspond pas à l’échelle à laquelle ses causes ou conséquences se produisent.

### **Exemple**

Pollution régionale gérée uniquement :

> municipalement.

---

# **54\. Scale Mismatch Can Produce Persistent Failure**

\[  
ProblemScale  
\\neq  
GovernanceScale  
\]

peut produire :

* externalités;  
* insuffisance de ressources;  
* décisions contradictoires.

### **Mais**

cela ne signifie pas automatiquement :

> monter toute la gouvernance d’un niveau.

Parfois il suffit :

> d’une interface intermunicipale.

---

# **55\. Solve the Interface Before Replacing the Institution**

Reprendre le chapitre 4\.

Lorsqu’un problème traverse plusieurs institutions, demander d’abord :

> faut-il créer une institution supérieure?

ou seulement :

> une meilleure interface?

### **Formulation**

> **A cross-scale problem may require cross-scale coordination without requiring institutional absorption.**

---

# **56\. Temporary Coordination Structures**

Certaines crises peuvent justifier :

> une coordination temporaire à grande échelle.

Exemple :

* catastrophe;  
* épidémie.

### **Donc**

\[  
TemporaryCentralization  
\\neq  
PermanentCentralization  
\]

### **Conditions**

* mandat;  
* durée;  
* audit;  
* retour de compétences.

---

# **57\. Emergency Scale Expansion**

Une institution locale peut temporairement céder :

> davantage de coordination

à un niveau supérieur.

Mais l’architecture devrait permettre :

\[  
EmergencyAuthority  
\\rightarrow  
Expiration/Review  
\]

sinon :

> pouvoir temporaire devient structure durable.

---

# **58\. Scale and Correction Latency**

Une décision globale peut être :

* cohérente;  
* mais lente à recevoir feedback local.

Donc :

\[  
Scale\\uparrow  
\]

peut augmenter :

\[  
FeedbackDistance  
\]

et potentiellement :

\[  
\\tau\_c  
\]

si les interfaces sont mauvaises.

---

# **59\. Local Feedback Must Travel Upward Without Being Flattened**

Un niveau supérieur a besoin :

> de synthèse.

Mais une synthèse peut supprimer :

* exceptions;  
* minorités;  
* incertitude.

Donc :

\[  
LocalExperience  
\\rightarrow  
Aggregation  
\]

doit préserver :

> suffisamment de structure.

---

# **60\. Aggregation Across Scales**

Une instance globale n’a pas nécessairement besoin :

> de toutes les données brutes.

Elle peut recevoir :

* agrégats;  
* claims validés;  
* artefacts;  
* anomalies.

### **Exemple**

\[  
LocalRawData  
\\rightarrow
