# Editorial Contract

## 1. Scope discipline

Every chapter must know what it owns and what it reserves.

A chapter may foreshadow later concepts but should not pre-solve them. The book should feel like a demonstration whose next question is generated by the previous answer.

## 2. Theory first, architecture second

Preferred order:

\[
Theory
\rightarrow
DesignSpace
\rightarrow
ExistingResponses
\rightarrow
ConcreteArchitecture
\rightarrow
Limits
\]

The correct rhetorical form is:

> In theory, a system with this problem requires property X. Existing systems partially realize X in several ways. One concrete architecture attempting to combine these requirements is kOA.

The wrong form is:

> kOA has module X, therefore civilizations need X.

## 3. Removal test

If all kOA references were removed, the main intellectual argument of a chapter should remain valid.

## 4. Formula protocol

For every important formula:
- formula;
- literal translation;
- conceptual meaning;
- status;
- empirical measurement only where justified.

Prefer prose when notation adds no structural clarity.

Final manuscript: roughly 8–12 recurrent canonical formulas/relations, plus rare chapter-local notation.

## 5. Epistemic statuses

Preserve:
- Fact;
- Interpretation;
- Hypothesis;
- Design principle;
- Implementation;
- Normative commitment.

A design preference must not disguise itself as science.

## 6. Counterexample protocol

Every attractive principle should meet its shadow:
- transparency → surveillance;
- expertise → technocracy;
- reputation → caste;
- standardization → lock-in;
- federation → fragmentation;
- fork → sectarianism;
- memory → ossification;
- narrative → cult/propaganda;
- coherence → conformity;
- determinism → reproducible error;
- openness → exposure or abuse.

Then derive a safeguard.

## 7. Systems vocabulary

Use systems terms only when they clarify a mechanism.

If an attractor, feedback loop or other term is analogical rather than formal, say so.

Do not turn civilization into a literal organism or collective mind.

## 8. Normative boundary

Never derive political legitimacy from efficiency.

\[
FunctionalEffectiveness \neq NormativeLegitimacy
\]

Never derive sovereignty from competence.

\[
Competence \neq Mandate
\]

Never derive human worth from reputation or competence.

## 9. Source discipline

Source external claims involving:
- history;
- quantitative facts;
- existing institutions;
- technologies;
- contested empirical claims.

Conceptual distinctions and design hypotheses can be argued directly, but should not be dressed as established laws.

## 10. Style

Target reader: serious, intelligent, non-specialist.

Tone:
- dense but readable;
- precise;
- concrete after abstraction;
- skeptical of its own claims;
- restrained.

Avoid:
- superlatives;
- revolution marketing;
- jargon for prestige;
- product-pitch language.

## 11. Chapter architecture

A strong chapter usually contains:
1. concrete opening problem;
2. mechanism;
3. one or two central distinctions;
4. dynamics/failure modes;
5. design consequences;
6. existing approaches;
7. concrete architecture;
8. objections/tests;
9. transition.

Flexible, not compulsory formatting.

## 12. Spiral rule

Concepts return at greater resolution. Deepen rather than repeat.

## 13. Narrative rule

Narrative can manifest the whole, compress complexity, route attention, retain lessons, simulate failure and support founder decentering.

But:

\[
NarrativeCoherence \neq StructuralCoherence
\]

Narrative must never become the evidence layer or mandatory mythology.

## 14. Function before product name

Prefer:
> "a portable knowledge artifact, later called Kristal"

before introducing the branded term.

Do not dump ecosystem names into the introduction.

## 15. Stable concepts vs evolvable implementations

More stable:
- coherence;
- losses;
- composition;
- portability;
- contextual expertise;
- non-domination;
- forkability;
- selective permeability;
- cumulative agency.

More contingent:
- exact module names;
- UI;
- weighting formulas;
- current software layout;
- steward institution;
- language-module maturity.

Write accordingly.

## 16. Founder discipline

Founder is never evidence.

The architecture should remain conceptually valid if:
- founder leaves;
- public instance diverges;
- another institution builds better implementation;
- King Klown disappears from institutional presentations.

## 17. Outcome discipline

Do not claim success because:
- code exists;
- demo works;
- platform is adopted;
- institution endorses it;
- founder is credible.

Success requires the relevant mechanism to produce the expected outcome under specified conditions.

## 18. Final standard

The book is strongest when it says:
- exactly what it means;
- exactly what it does not mean;
- why the mechanism matters;
- what tradeoff it creates;
- what would make us change our minds.
